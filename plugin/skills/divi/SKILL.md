# Working on a Divi site

New builds are block-first (see the wp-studio:block-themes skill), and moving a site off Divi is
the wp-studio:divi-to-blocks skill. This skill is for keeping an existing Divi site healthy until
then. Read the whole "Before you edit" section before any write.

## Before you edit

### 1. Find out which Divi you are on

Divi 4 and Divi 5 store pages in completely different formats, so every search, edit and
migration step depends on this.

```bash
wpsite wp acme theme list --fields=name,status,version
wpsite wp acme post get 123 --field=content | head -c 400
```

- `[et_pb_section …][et_pb_row …][et_pb_text …]` → **Divi 4 shortcodes.**
- `<!-- wp:divi/section {…} -->` → **Divi 5 block comments.** Attributes are deeply nested JSON,
  including `$variable(...)$` design-token references. A search for `et_pb_` finds nothing.

Back up before any content write (`wpsite backup acme --post 123`). Divi 5 attribute JSON is easy
to corrupt with string edits; prefer editing in the builder for anything beyond a text swap.

### 2. Is the content you want to change really in this post?

**Global modules live in the Divi Library, not in the page.** A section shared across pages is a
Divi Library item (post type `et_pb_layout`) referenced from the page with
`global_module="<library post ID>"`. At render time Divi pulls the content from the library item,
so editing only the page has no visible effect, even though the page holds a copy. Edit the
library item; also update the page copy if you edit by WP-CLI, so the builder stays consistent.
(Observed on a Divi 4 site.)

```bash
wpsite wp acme post get 123 --field=content | grep -o 'global_module="[0-9]*"' | sort -u
wpsite wp acme post get <library-ID> --fields=ID,post_type,post_title
```

Plain words for the operator: "That section is shared. Change it once in Divi → Divi Library and
every page that uses it updates."

**The header, footer and post templates live in the Theme Builder**, not in page content.

## After any content edit: clear that post's Divi CSS cache

**Rule: after changing a Divi post's content by any route other than the Divi builder, delete
`wp-content/et-cache/<post-id>/` and purge the page cache. Then look at the page.**

Why: Divi writes a static CSS bundle per post into `wp-content/et-cache/<post-id>/`. It
invalidates that bundle from a `save_post` callback (`ET_Core_PageResource::save_post_cb`) that
the **theme** registers. A WP-CLI write run with `--skip-themes` (common, to silence plugin
notices) never loads Divi, so the callback never runs and the stale bundle survives. This was
verified on Divi 4.27 by listing the `save_post` callbacks with and without `--skip-themes`.

Why it hurts: Divi's generated CSS is keyed by **position** — `.et_pb_section_0`,
`.et_pb_section_1`, … in document order — not by an ID. If an edit changes how many sections a
post has, every rule shifts onto a different section. Removing two leading sections left the
real content section at index 0, where it inherited the deleted header's dark background: dark
text on dark navy, from markup that was entirely correct. The HTML passes every string check;
only the cached CSS is wrong.

```bash
wpsite backup acme                                   # the rm below needs a fresh backup
wpsite sh acme 'rm -rf wp-content/et-cache/123'      # path relative to the WordPress root
wpsite purge acme
```

Then load the page in a browser with a cache-busting query (`?cb=<random>`) and look at it. A
host or page-cache purge alone does **not** clear `et-cache` (page caches: the wp-studio:caching
skill).

The same cache exists on Divi 5 (a Divi 5 site regenerated byte-identical CSS after `et-cache`
was cleared, which is how a theme regression was told apart from a stale cache). Whether Divi 5's
own invalidation behaves the same under `--skip-themes` is **UNVERIFIED**; clear the folder
anyway. Elegant Themes' own help documents the dashboard route on Divi 4: Divi → Theme Options →
Builder → Advanced → Static CSS File Generation → Clear.

## Theme Builder chrome copied into a post

**Symptom:** a post renders a second header or nav bar, or a blog card's summary shows raw
shortcodes such as `[dsm_button …]`.

**Cause:** the post's own content holds a full copy of the site header/footer (a full layout
loaded from the Divi Library, or a builder save going wrong). Archive cards show raw shortcodes
because an empty `post_excerpt` makes WordPress build the excerpt from the first words of the
content, which is now the pasted header.

**Detect it** by a marker only the Theme Builder may own — a menu module (`[et_pb_menu` on Divi
4) plus something footer-only, such as the footer's logo file — scoped to
`post_type IN ('post','page') AND post_status='publish'`:

```bash
wpsite wp acme db query "SELECT ID, post_title FROM wp_posts
  WHERE post_type IN ('post','page') AND post_status='publish'
  AND post_content LIKE '%[et_pb_menu%'"
```

(Use `wp db prefix` if the table prefix is not `wp_`.)

- **Never use a `global_module` ID as the marker.** Shared library items legitimately appear in
  ordinary pages; on one site the footer's library module was also in twelve real pages.
- **A detector needs a positive control.** "Nothing found" is also what a detector with drifted
  markers returns. Assert it flags the live Theme Builder header/footer (resolve their IDs from
  `et_template` data, not hard-coded IDs) and does not flag a page that shares a library module.
  Fail loudly if either control cannot run.
- **Fix:** back up the post, remove the duplicated sections, then clear `et-cache/<id>` as above.

**Before blaming the client, check the update log.** On one incident Divi had auto-updated
hours before the client noticed, and that release's changelog named a fix for layouts lost when
switching editors in the current WordPress block editor. Revision history proves *when* content
changed, not *who or what* changed it. Compare the theme folder's modification time
(`wpsite sh acme 'stat -c %y wp-content/themes/Divi'`) and the theme's `changelog.txt`, and record
the cause as unestablished when the evidence does not settle it.

## Updates: keep them on, hold only cross-major builder jumps

**Rule: Divi updates stay on, like everything else. Hold back only a cross-major builder upgrade
(Divi 4 → Divi 5).** The policy and the mu-plugin that enforces it belong to the
wp-studio:updates-and-hardening skill; do not restate or override it here.

The v1 kit said "pin Divi and turn auto-update off on production". That was wrong and is
withdrawn: a pinned site stops getting security and compatibility fixes, and a pin outlives the
reason for it. The history behind it is still worth knowing:

- A Divi **5.6.2 → 5.7.0** update broke a site's Theme Builder header: the SVG logo collapsed to
  0 height and responsive show/hide stopped, so desktop and mobile menus both rendered. Clearing
  `et-cache` regenerated identical broken CSS, which proved it a release regression. The site was
  rolled back, then **5.7.4 fixed it**. A rollback is a few days' bridge to the next release,
  never a standing pin.
- Divi 4 patch releases install unattended through the normal WordPress auto-update path once
  the Elegant Themes licence is active on the site (observed on Divi 4.27).

After any Divi update, check the header, nav and logo at desktop and phone widths.

**Installing an exact version** (rollback): Divi is not on wordpress.org. Download the exact
version from the Elegant Themes account, check `Divi/style.css` inside the zip for the version,
then upload and install it, clear the whole `et-cache` folder and purge:

```bash
wpsite deploy acme work/Divi-5.7.4.zip wp-content/upgrade-studio/Divi-5.7.4.zip
wpsite wp acme theme install wp-content/upgrade-studio/Divi-5.7.4.zip --force
wpsite sh acme 'rm -rf wp-content/et-cache/* wp-content/upgrade-studio'
wpsite purge acme
```

The licence lives in the `et_automatic_updates_options` option (a username and API key). Treat
the key as a secret: never print it into the transcript.

## Custom CSS on Divi 5

**Rule: on a Divi 5 site, put custom CSS in an mu-plugin** (template and rules in the
wp-studio:block-themes skill, "Durable custom CSS").

On one Divi 5.6.2 site, Divi's Theme Options custom CSS (`et_divi[custom_css]`) was not printed
on the front end, and WordPress core "Additional CSS" was absent from the served HTML too. CSS
saved in either place silently did nothing. Whether this holds on later Divi 5 releases is
**UNVERIFIED** — settle it on the site in front of you:

```bash
curl -s "https://example.com/?cb=$RANDOM" | grep -c 'id="wp-custom-css"'
```

This is a Divi 5 finding. On Divi 4 and on other themes, Additional CSS renders normally.

## Divi 5 front-end runtime failures

On one Divi 5 site, the front-end code for **entrance animations** (`.et_animated`) and
**interactions** (`data-interaction-trigger`, click-to-toggle popups) never initialised: no
JavaScript errors, every asset HTTP 200. Animated elements stayed at `opacity:0` (invisible), and
popup sections never got their hidden state, so they leaked into the page.

When the site must stay on Divi, fix it in an mu-plugin: force `.et_animated{opacity:1}`, hide the
popup sections by default, and reimplement the toggle in plain JavaScript using the page's own
`data-interaction-trigger` → `et-interaction-target-*` mapping. Register the click listener on
`window` in the capture phase and call `stopImmediatePropagation()` so it runs before Divi's
partly-firing handler. Re-test after each Divi update and remove the workaround once fixed.

## Divi-ecosystem plugins on Divi 5

Older Divi add-on plugins can call Divi 4 classes (`ET_Builder_Element`) that Divi 5 loads only
conditionally, which gives intermittent fatal errors on uncached requests. Do not patch the add-on
(an update wipes the patch); update it, replace it, or remove it after checking that its modules
are not used in content.

## Noise you can ignore

- Console warning `ETmodules … glyf: Glyph bbox was incorrect` — Divi's icon font; harmless.
- Empty `@font-face { src: url(); }` rules in `<style id="et-divi-userfonts">` when fonts come
  from an external kit: `document.fonts.check()` reports errors, but the fonts render.
